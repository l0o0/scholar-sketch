## 领取与交付

1. 读取 Linear 中已接受任务及现有 PR，避免重复领取。当前聊天可提供明确授权，但持久任务状态仍回写原任务，不另建一套 GitHub issue 待办。
2. 检查工作区、远端基线、相关实现与现行准则。有实际冲突时按 AGENTS.md 说明来源、适用阶段、后果与替代方案。用户明确调整的决定优先；不把普通新需求默认为撤销旧规则。
3. 用可观察行为确定范围。局部修复可以直接在任务描述中写触发条件、预期结果和非目标；跨模块变更才补充设计。数据迁移、Obsidian 同步、大范围白板重构应先提醒当前试点范围并厘清实施顺序，不能偷偷缩成原型。
4. 在干净分支或独立工作区修改，保留其他在途工作。复现缺陷，选择最小有效测试，完成实现；不要用重写测试期望掩盖失败。
5. 执行相关检查，记录实际结果。独立 Agent 从需求和差异检查真实入口、失败路径、消费者与遗漏；其报告不等于维护者批准票。
6. 建立 PR，附任务、验证和剩余限制；维护者验收合并。需要分发时继续执行发布流程，不能把“PR 已开”或“CI 通过”写成“已发布”。

已通过的检查只在改动影响其结论时重跑。首次实现后最多两轮针对性修复；相同失败反复出现且没有新证据时停止自动修复，留下复现、诊断和所需帮助。范围扩大到真实用户 profile、数据迁移或超出约定预算时，暂停受影响步骤，继续不受影响且已授权的工作。

## 检查入口

使用仓库锁定的 pnpm 9.15.9 和 CI 的 Node 22（至少 22.16.0，SQLite 测试依赖该版本提供的 FTS5 与 statement metadata 支持）：

```sh
pnpm install --frozen-lockfile
pnpm run verify
```

`verify` 顺序执行归属检查、lint、unit、fake、build。unit 和 fake 各自调用 `test:prepare` 构建依赖，因此可以单独执行，不依赖旧的 dist。CI 拆为并行 job，但调用同一入口命令；`Sketch checks` 仅在全部 job 成功时通过，job 失败、取消、跳过都不能冒充成功。main 已配置 PR 与最新 `Sketch checks` 门禁，限定 GitHub Actions 来源，对管理员同样生效；不要求第二人的批准票。仓库设置可能变化，执行合并前仍须核对实际规则，不能通过绕过检查推进任务。

单测允许既有的条件性跳过，报告须单列跳过数量与原因。目前 Linux CI 不执行 macOS 专属快捷键用例；未配置 `ZOTERO_NOTE_MARKDOWN_TRANSLATOR` 时，真实 Zotero Markdown translator 用例跳过。这些能力不能仅凭汇总绿色声称已验证，也不能把新失败随意改成 skip。

| 命令                         | 证明范围                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| `pnpm run test:suites:check` | `test/` 与 `packages/fake-zotero/test/` 下每份测试恰有一个归属，且 runner 类型匹配 |
| `pnpm run test:unit`         | Node 中的局部与集成行为                                                            |
| `pnpm run test:fake-zotero`  | 先构建 fake 包，再执行 fake 包及根目录集成测试                                     |
| `pnpm run build`             | 类型与插件打包                                                                     |
| `pnpm test`                  | 真实 Zotero runner，需要本机宿主；不由 Node suite 代替                             |

测试清单唯一维护在 `scripts/test-suites.mjs`，不能只在命令里添加通配符。Node 测试显式导入 `node:test`；原生 Mocha/Zotero 测试归入宿主组。新增测试目录或 runner 时同时扩展发现范围和对应执行入口，并证明漏归属/错分会失败。归属检查不证明测试断言本身充分。

UI 与 iframe 交互可使用 [Fake Zotero](fake-zotero.md)。原生窗口、启动/卸载、真实文件保存、关闭重开仍需隔离 Zotero profile 验收。Fake localStorage 的成功不能记录为真实文件落盘。

## 一次任务要留下什么

直接使用 PR 模板，不另建记录系统：

- 原任务链接、用户目标、验收标准和非目标。
- 固定提交、执行的命令/CI run；失败与未测部分分开写。
- 对重要修复，记录修复前失败、修复后通过的证据；新门禁用负例证明会拒绝错误。
- 独立审查结论、必要宿主证据、已知限制与回退方式。
- 例外的理由、范围和结束条件；普通低风险任务无需编造例外或另写审批表。
- 实际人工审查时间、返工轮次、环境失败与可获得的任务成本；未知就标未知，不编造指标。

Linear 状态按实际结果更新：实现中、待审查、待验收、待发布、已发布可以写入任务正文；沿用团队已有状态字段，不为了试点擅自改整个团队工作流。仅有基础设施改动无需插件版本发布，合并并确认 main 上的检查生效后即可完成该任务。
